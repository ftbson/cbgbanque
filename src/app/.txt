AUDIT COMPLET ET CORRECTION DÉFINITIVE DU SYSTÈME MULTILINGUE, DES ROUTES ET DE L'AUTHENTIFICATION

Je veux que tu interviennes directement sur mon projet pour résoudre définitivement plusieurs problèmes qui persistent malgré les corrections précédentes.

Je ne veux plus de corrections superficielles, de systèmes de traduction improvisés ni de modifications qui déplacent simplement le problème ailleurs.

Tu dois examiner le code existant, comprendre l'origine des dysfonctionnements, supprimer les mécanismes défectueux et mettre en place une architecture cohérente.

1. PROBLÈME URGENT : LES CLÉS DE TRADUCTION S'AFFICHENT SUR LA PAGE D'ACCUEIL

Actuellement, lorsque j'ouvre la page d'accueil, au lieu d'afficher les vrais textes, le site affiche directement des clés techniques de traduction.

Exemples de ce qui apparaît :

common.appName

hero.badge

hero.title

hero.titleHighlight

hero.subtitle

hero.ctaPrimary

hero.ctaSecondary

hero.trust1

features.tag

features.title

features.subtitle

features.items.account.title

features.items.account.description

cta.statsTag

testimonials.tag

testimonials.title

footer.bannerTitle

footer.legalText

footer.links.help

footer.links.privacy

Et beaucoup d'autres clés apparaissent également.

C'est un dysfonctionnement majeur. Je ne veux plus voir ces clés techniques sur aucune page.

Ce que tu dois faire :

Identifier précisément le mécanisme qui provoque l'affichage de ces clés.

Examiner les fichiers de traduction, les composants, les layouts, les fonctions de traduction, les imports et les éventuelles configurations de localisation.

Identifier les fichiers qui génèrent ou permettent ce système défectueux.

Supprimer l'architecture de traduction par clés qui provoque ces problèmes, notamment si elle repose sur des dictionnaires JSON, des fonctions de traduction dynamiques ou des configurations de remplacement de texte.

Supprimer les fichiers devenus inutiles uniquement après avoir vérifié qu'ils ne sont plus utilisés.

Ne pas laisser d'anciens mécanismes de traduction coexister avec la nouvelle architecture.

Je ne veux plus de textes affichés sous forme de clés telles que hero.title, nav.login ou footer.legalText.

2. NOUVELLE ARCHITECTURE : DES PAGES DISTINCTES PAR LANGUE

Je veux que le système multilingue repose sur de véritables pages et fichiers distincts.

Les dossiers FR, DE et ES ont déjà été créés. Vérifie leur état actuel et exploite-les correctement.

Chaque espace doit contenir ses propres pages, composants et fichiers nécessaires.

Par exemple :

FR : version française.

DE : version allemande.

ES : version espagnole.

Les contenus doivent être écrits directement dans les fichiers de chaque espace linguistique.

Je ne veux plus d'un système centralisé dans lequel une page unique récupère ses textes à partir d'un dictionnaire de traductions.

Je veux que les fichiers des pages soient réellement séparés.

Important :

Ne supprime pas les fichiers existants sans avoir vérifié leurs dépendances.

Ne casse pas les fonctionnalités existantes.

Ne réécris pas toute l'application inutilement.

Conserve les fonctionnalités, le design, les composants, les styles et la logique métier qui sont déjà fonctionnels.

3. LES ROUTES DOIVENT ÊTRE IDENTIQUES DANS LES TROIS LANGUES

Je veux que les noms des pages et les slugs restent identiques dans les trois langues.

La langue change uniquement le préfixe de l'URL et le contenu affiché, pas les noms des routes.

Exemple :

Français

Allemand

Espagnol

/FR

/DE

/ES

/FR/login

/DE/login

/ES/login

/FR/register

/DE/register

/ES/register

/FR/dashboard

/DE/dashboard

/ES/dashboard

/FR/dashboard/settings

/DE/dashboard/settings

/ES/dashboard/settings

Le nom des routes doit être exactement le même dans les trois espaces.

Je ne veux pas que DE ou ES utilisent des noms de pages différents de ceux de FR.

Par exemple, si la page d'inscription en français utilise /FR/register, alors l'allemand et l'espagnol doivent également utiliser /DE/register et /ES/register.

Ne transforme pas /register en un autre slug dans les versions allemandes ou espagnoles.

Même règle pour la connexion, le dashboard, les paramètres, les profils, les pages internes et toutes les autres routes.

4. LA LANGUE DOIT RESTER ACTIVE SUR TOUT LE PARCOURS

Lorsque je sélectionne DE, je dois entrer dans l'espace allemand.

À partir de ce moment :

Tous les liens doivent pointer vers des routes /DE.

Toutes les pages doivent utiliser les fichiers allemands.

Tous les boutons doivent respecter le préfixe /DE.

La connexion doit rester dans /DE.

L'inscription doit rester dans /DE.

Le dashboard doit rester dans /DE.

Les paramètres doivent rester dans /DE.

Les redirections doivent rester dans /DE.

Les liens internes doivent rester dans /DE.

Même fonctionnement pour ES et FR.

La langue ne doit jamais changer involontairement au cours d'une navigation.

Seule une action explicite dans le sélecteur de langue doit modifier le contexte linguistique.

5. LES TEXTES DES PAGES DOIVENT ÊTRE FIDÈLES À LA VERSION FRANÇAISE

La version FR doit servir de référence pour les pages et leurs structures.

Je ne veux pas que les versions allemandes et espagnoles inventent de nouvelles pages, de nouveaux noms de routes, de nouvelles structures de navigation ou de nouveaux parcours.

Les pages DE et ES doivent reprendre exactement les mêmes structures, les mêmes fonctionnalités, les mêmes boutons, les mêmes formulaires et les mêmes parcours que FR.

Seul le contenu textuel visible doit être traduit littéralement dans la langue correspondante.

Ne réécris pas les textes.

Ne modifie pas la logique métier.

Ne crée pas de nouveaux parcours de navigation spécifiques à une langue.

Ne renomme pas les routes.

Ne modifie pas les fonctionnalités.

6. CORRIGER LE SÉLECTEUR DE LANGUE

Le sélecteur de langue doit fonctionner réellement.

Lorsque je suis sur /FR, je peux sélectionner DE et être redirigé vers /DE.

Lorsque je suis sur /DE, je peux sélectionner ES et être redirigé vers /ES.

Lorsque je suis sur /ES, je peux sélectionner FR et être redirigé vers /FR.

Si je suis sur une page interne, le changement de langue doit me conduire à la page équivalente dans la langue sélectionnée, lorsque celle-ci existe.

Exemples :

/FR/login vers /DE/login.

/FR/register vers /ES/register.

/DE/dashboard vers /FR/dashboard.

/ES/dashboard/settings vers /DE/dashboard/settings.

Le sélecteur de langue ne doit pas simplement changer le texte de la page actuelle. Il doit naviguer vers la véritable route de l'espace linguistique choisi.

7. PROBLÈME D'AUTHENTIFICATION : ERREUR DE CONNEXION AU SERVEUR

Actuellement, lorsque j'essaie de me connecter, j'obtiens une erreur indiquant que l'application ne parvient pas à accéder au serveur.

Je veux que tu traites ce problème comme une priorité.

Ne te contente pas de supposer que le serveur est indisponible.

Je veux que tu recherches précisément la cause.

Examine :

Les routes API d'authentification.

Les endpoints de connexion et d'inscription.

Les URL utilisées par le frontend.

Les configurations backend.

Les variables d'environnement.

Les configurations de base de données.

Les middlewares.

Les cookies.

Les sessions.

Les JWT et leur validation.

Les redirections après connexion.

Les redirections après inscription.

Les configurations CORS si elles sont pertinentes.

Les erreurs HTTP.

Les erreurs de réseau.

Les éventuels changements apportés au système multilingue.

Les chemins API incorrectement configurés.

Les appels qui pourraient être envoyés vers une mauvaise route.

Les éventuelles erreurs de compilation ou d'exécution.

Je veux que tu identifies la cause réelle de l'erreur et que tu corriges le code responsable.

Ne fais surtout pas ceci :

Ne désactive pas l'authentification.

Ne supprime pas les contrôles de sécurité.

Ne remplace pas le système de connexion par un faux système.

Ne simule pas une connexion réussie.

Ne crée pas de données fictives pour masquer le problème.

Ne modifie pas arbitrairement les identifiants ou les secrets.

Ne prétends pas que le serveur fonctionne si tu ne l'as pas vérifié.

Si la cause dépend d'une variable d'environnement, d'une base de données, d'un service externe ou d'un accès que tu ne possèdes pas, indique-le clairement et précise ce qui doit être configuré.

8. L'AUTHENTIFICATION DOIT RESPECTER LA LANGUE

Une fois le système d'authentification corrigé :

/FR/login doit utiliser la version française.

/DE/login doit utiliser la version allemande.

/ES/login doit utiliser la version espagnole.

Même principe pour l'inscription.

Après connexion :

Une connexion depuis /FR/login doit conduire vers /FR/dashboard.

Une connexion depuis /DE/login doit conduire vers /DE/dashboard.

Une connexion depuis /ES/login doit conduire vers /ES/dashboard.

Après inscription, le même principe doit être respecté.

Après déconnexion, la redirection doit également conserver la langue active.

Examine tous les mécanismes de redirection afin qu'aucun ne renvoie systématiquement vers FR.

Vérifie :

Les formulaires.

Les pages de profil.

Les routes internes.

Les redirections.

10. PROCÉDURE DE TRAVAIL

Je veux que tu travailles méthodiquement.

Étape 1 : Audit

Examine l'ensemble de l'architecture du projet et identifie les causes des problèmes.

Étape 2 : Identifier les mécanismes défectueux

Repère les fichiers, composants, configurations et routes qui provoquent :

L'affichage des clés de traduction.

Les incohérences entre FR, DE et ES.

Les routes incorrectes.

Les redirections vers FR.

Les erreurs de connexion au serveur.

Étape 3 : Corriger l'architecture

Supprime les mécanismes de traduction défectueux lorsqu'ils sont responsables des problèmes.

Finalise les dossiers FR, DE et ES.

Corrige les routes, les liens, les redirections et l'authentification.

Étape 4 : Vérification

Teste les fonctionnalités que l'environnement permet réellement de tester.

Vérifie le serveur, les routes, les pages, l'authentification, les redirections et les changements de langue.

Étape 5 : Compte rendu

À la fin, indique :

Les problèmes identifiés.

Les causes réelles.

Les fichiers modifiés.

Les fichiers supprimés et la raison de leur suppression.

Les corrections apportées.

Les tests effectués.

Les tests qui n'ont pas pu être exécutés.

Les éventuelles configurations manquantes.

Ne me donne pas uniquement un plan. Je veux que tu exécutes les corrections directement dans le projet.

OBJECTIF FINAL

Je veux une application stable, cohérente et fonctionnelle.

Je veux que les clés techniques de traduction disparaissent définitivement de l'interface.

Je veux trois espaces linguistiques réels, /FR, /DE et /ES, avec les mêmes routes, les mêmes fonctionnalités et les mêmes parcours.

Je veux que le changement de langue modifie réellement l'URL et que toute navigation respecte l'espace linguistique actif.

Je veux que la connexion et l'inscription fonctionnent correctement, sans erreur de communication avec le serveur.

Je veux que tu vérifies ce que tu modifies et que tu ne me présentes pas des résultats de tests que tu n'as pas réellement exécutés.

Commence par auditer le projet, puis effectue les corrections nécessaires directement dans le code.
